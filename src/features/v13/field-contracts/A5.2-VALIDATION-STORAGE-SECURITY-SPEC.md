# 13.1-A5.2 — Spécification du stockage et de la sécurité ValidationConfig

**Statut : spécification documentaire — approbation requise**  
**Contrat ciblé : `ValidationConfig 1.0.0`**

## 1. Objectif

Définir précisément le futur stockage PostgreSQL, la normalisation, la
validation serveur, la sauvegarde atomique, `no_change`, l’audit commun, la RPC
administrative et le vérificateur non mutatif nécessaires à un brouillon
`ValidationConfig 1.0.0`.

Cette spécification prépare A5.3 sans créer de comportement exécutable.

## 2. Statut documentaire

A5.2 ne crée aucun SQL, migration, RPC, service, validateur, interface, test ou
consommateur. Aucune configuration n’est active. Le stockage décrit reste un
brouillon administratif sans effet métier.

## 3. Références gelées

- `ValidationConfig 1.0.0` et les fonctions pures A3.2;
- `A5.1-VALIDATION-DRAFT-CONTRACT.md`;
- `public.relation_fields` créé et enrichi par A1;
- `public.relation_field_config_audit` créé par A3;
- extension versionnée de l’audit et RPC sécurisée A4.2;
- stratégie `deny wins`;
- objets explicitement qualifiés, propriétaire `postgres`,
  `SECURITY DEFINER`, `search_path = pg_catalog`;
- révocation `PUBLIC`/`anon`, exécution `authenticated`;
- aucune consommation avant activation distincte.

## 4. Décisions finales

1. Longueurs comptées en points de code Unicode.
2. `allowedValues` : maximum 100 valeurs scalaires non nulles, chaînes limitées
   à 500 points de code, JSON total limité à 64 Kio, doublons stricts refusés.
3. Comparaison stricte par type, ordre conservé et significatif.
4. `errorMessages` : six clés fonctionnelles fermées, texte brut non vide,
   maximum 300 points de code après normalisation des espaces extérieurs.
5. Aucune traduction imbriquée en version 1.0.0.
6. Une règle devenue incompatible reste visible et bloque une nouvelle
   sauvegarde tant qu’elle n’est pas corrigée.
7. Audit commun uniquement; aucun audit pour `no_change`.
8. `technical_name_locked` seul ne bloque pas ValidationConfig.
9. Aucun SQL, JavaScript, callback ou langage d’expression configurable.

## 5. Architecture de stockage

### Table et clé

| Élément | Recommandation |
|---|---|
| Table | `public.relation_fields` |
| Clé stable interne | `relation_fields.id` |
| Identité logique vérifiée | couple immuable `(table_name, field_name)` |
| Colonne | `validation_rules` |
| Type existant | `jsonb NOT NULL` |
| Défaut existant | `'{}'::jsonb` |
| Statut | `configuration_status`, hors ValidationConfig |

La colonne `validation_rules` existe déjà depuis A1. Créer
`validation_config` dupliquerait la responsabilité et risquerait une divergence.
A5.3 devrait donc consolider la colonne existante, sans table métier et sans
seconde colonne concurrente.

### Absence et héritage

- `{}` : aucune configuration ValidationConfig préparée pour cette ligne;
- objet canonique à sept clés toutes à `null` : brouillon explicitement préparé
  et entièrement hérité;
- objet canonique avec au moins une valeur non nulle : brouillon explicite;
- SQL `NULL` : interdit par la nullabilité existante.

La distinction `{}`/objet canonique doit être préservée lors du chargement
diagnostique. Pour la comparaison d’une sauvegarde, `{}` est normalisé vers
l’objet canonique hérité; une première sauvegarde entièrement héritée est donc
`no_change` sur le plan fonctionnel et ne doit pas écrire uniquement pour
remplacer `{}`.

### Version

Comme A4.2 :

- la RPC reçoit `p_contract_version`;
- seule `1.0.0` est acceptée;
- la version est enregistrée dans l’audit commun;
- aucune propriété `configurationStatus` n’est ajoutée au JSON;
- aucune seconde colonne de version n’est nécessaire dans `relation_fields`
  tant qu’une seule version est supportée.

### Index

Aucun index GIN sur `validation_rules` n’est recommandé en A5.3 : la sauvegarde
retrouve une ligne par son identité stable et les consommateurs restent
déconnectés. L’index d’audit existant
`(relation_field_id, changed_at DESC)` suffit. Tout index supplémentaire devra
être justifié par une requête réelle mesurée.

### Lignes existantes

Le défaut `{}` est conservé. Aucun backfill métier n’est nécessaire. Une
contrainte future peut être ajoutée `NOT VALID`, puis validée séparément après
inventaire. Aucune ligne n’est supprimée ou corrigée automatiquement.

## 6. Forme JSON canonique

La valeur stockée canonique contient exactement sept clés configurables :

```json
{
  "requiredOverride": null,
  "minimumLength": null,
  "maximumLength": null,
  "minimumValue": null,
  "maximumValue": null,
  "allowedValues": null,
  "errorMessages": null
}
```

Toutes les clés sont conservées explicitement, y compris celles à `null`.
Aucune donnée additionnelle n’est conservée. `schemaVersion` reste dans le
contrat d’échange client et le paramètre RPC, mais n’est pas dupliqué dans
`validation_rules`; `contract_version` de l’audit en porte la preuve persistée.

Ordre canonique conceptuel pour la sérialisation et les diagnostics :

1. `allowedValues`;
2. `errorMessages`;
3. `maximumLength`;
4. `maximumValue`;
5. `minimumLength`;
6. `minimumValue`;
7. `requiredOverride`.

PostgreSQL `jsonb` ne garantit pas un ordre de présentation. La comparaison doit
utiliser l’égalité `jsonb` après construction canonique, jamais une chaîne JSON
brute.

## 7. Normalisation

Trois opérations demeurent distinctes :

1. **normalisation déterministe** : forme et représentation;
2. **validation contractuelle** : types, bornes et conflits internes;
3. **compatibilité contextuelle** : type et protections réels du champ.

Normalisation conceptuelle :

1. exiger un objet JSON simple;
2. vérifier `p_contract_version = '1.0.0'`;
3. refuser toute clé hors liste blanche;
4. insérer chaque clé absente avec `null`;
5. préserver strictement `false` et `0`;
6. refuser chaînes numériques, `NaN`, infinités et types non JSON;
7. exiger des entiers non négatifs pour les longueurs;
8. refuser minimum de longueur supérieur au maximum;
9. exiger des nombres JSON finis pour les bornes;
10. refuser minimum numérique supérieur au maximum;
11. normaliser et valider `allowedValues`;
12. normaliser et valider `errorMessages`;
13. construire un nouvel objet à sept clés;
14. ne jamais corriger silencieusement une valeur invalide.

### Unicode

- JavaScript futur : `Array.from(value).length`;
- PostgreSQL futur : `char_length(value)`, documenté et testé avec des paires de
  substitution représentatives;
- `String.length` ne peut être la seule référence côté client;
- une séquence visuelle composée de plusieurs points de code peut compter pour
  plusieurs caractères;
- aucune segmentation par graphème n’est requise en 1.0.0.

## 8. Compatibilité de type

La RPC retrouve le champ dans `relation_fields`, verrouille la ligne et utilise
`field_type` ainsi que les métadonnées physiques comme autorité contextuelle.

| Famille réelle | requiredOverride | longueurs | bornes numériques | allowedValues |
|---|---:|---:|---:|---:|
| `short_text`, `long_text` | Oui | Oui | Non | Chaînes |
| `number`, `currency` | Oui | Non | Oui | Nombres compatibles |
| `boolean` | Oui | Non | Non | Booléens |
| `date`, `datetime` | Oui | Non | Non | Refus en 1.0.0 |
| `single_select` | Oui | Non | Non | Scalaires compatibles au type de valeur |
| `multi_select` | Oui | Non | Non | Univers de scalaires individuels |
| `relation` | Sous contrainte structurelle | Non | Non | Refus si champ protégé/FK |
| `photo`, `file` | Sous contrainte | Non | Non | Refus |
| `calculated` | Refus | Refus | Refus | Refus |
| type absent/inconnu | Refus conservateur | Refus | Refus | Refus |

Les types fonctionnels non présents dans la liste A1 ne doivent pas être
inventés par la RPC. Toute propriété incompatible produit
`incompatible_field_type`; aucune propriété n’est ignorée.

Les métadonnées physiques restent prioritaires :

- `NOT NULL` l’emporte sur `requiredOverride=false`;
- `physical_maximum_length` borne `maximumLength`;
- précision et échelle physiques bornent les valeurs numériques;
- un type physique devenu incompatible provoque `schema_changed`.

## 9. `allowedValues`

Règles futures obligatoires :

- `null` pour la propriété signifie aucune liste déclarative;
- tableau de 0 à 100 éléments;
- éléments : `string`, nombre JSON fini ou `boolean`;
- élément `null`, objet, tableau imbriqué, fonction ou expression refusé;
- chaîne limitée à 500 points de code;
- taille UTF-8 du JSON sérialisé canonique ≤ 65 536 octets;
- doublons stricts refusés;
- ordre fourni conservé;
- aucune déduplication ou réorganisation silencieuse.

Clé de doublon stricte recommandée :

```text
type JSON + représentation JSON canonique de la valeur
```

Ainsi `"1"` et `1`, ainsi que `true` et `"true"`, restent distincts.

Pour une sélection multiple, `allowedValues` décrit l’univers individuel
permis; la valeur métier future pourra être un tableau. Chaque élément devra
appartenir à cet univers. Une liste métier vide pourra être valide lorsque
`requiredOverride !== true`; si `true`, au moins un élément sera requis. Ces
règles ne sont pas consommées en A5.2/A5.3.

## 10. `errorMessages`

Clés autorisées exclusivement :

- `requiredOverride`;
- `minimumLength`;
- `maximumLength`;
- `minimumValue`;
- `maximumValue`;
- `allowedValues`.

Règles :

- objet JSON ou `null`;
- maximum six messages, un par clé;
- aucune clé générique, technique, de sécurité ou inconnue;
- valeur textuelle brute seulement;
- espaces de début et de fin supprimés avec une convention Unicode déterministe;
- chaîne vide après normalisation refusée;
- maximum 300 points de code;
- HTML, script, URL `javascript:` et interpolation exécutable refusés;
- Markdown n’est jamais rendu comme contenu actif;
- données sensibles interdites;
- aucune structure multilingue ou objet de traduction.

Le texte saisi conserve sa langue. Les erreurs de sécurité, autorisation,
contrat, schéma, stockage et réseau utilisent toujours les messages système.

## 11. Champs protégés

Protection absolue si une condition est vraie :

- nom exact `support_id`;
- clé primaire;
- clé étrangère protégée;
- identity;
- generated;
- `id`, `created_at`, `updated_at`, `deleted_at`, `auth_user_id`;
- `photo_principale_url`, `photo_miniature_url`,
  `visuel_actuel_cadre`;
- champ système, calculé ou virtuel;
- champ explicitement non configurable.

Le suffixe `_id` reste un signal de la politique gelée 1.0.0, mais la future
RPC doit d’abord utiliser les classifications physiques précises et les noms
protégés, puis appliquer cette règle contractuelle complémentaire. Il ne doit
pas constituer l’unique preuve lorsqu’une métadonnée plus précise existe.

`technical_name_locked` seul ne bloque pas ValidationConfig. Il interdit le
renommage technique, pas la validation administrative.

Une règle devenue protégée après modification du schéma reste visible en
diagnostic, n’est pas supprimée et ne peut être resauvegardée comme valide.

## 12. Modèle de sécurité

La future capacité respecte :

```text
client Administrateur
  → RPC publique unique
    → auth.uid() présent
    → current_app_role() = 'Administrateur'
    → ligne relation_fields verrouillée
    → protection + contrat + type + normalisation
    → no_change OU update catalogue + audit atomique
```

Exigences :

- `SECURITY DEFINER`;
- propriétaire `postgres`, conforme à A4.2;
- `SET search_path = pg_catalog`;
- chaque objet applicatif qualifié `public.`;
- révocation `PUBLIC` et `anon`;
- `EXECUTE` accordé uniquement à `authenticated` et au propriétaire;
- aucune écriture directe accordée sur `relation_fields` ou l’audit;
- aucun nom de table fourni comme cible SQL;
- aucun `EXECUTE`, `format()` dynamique ou SQL construit;
- liste blanche de deux tables écrites :
  `public.relation_fields` et `public.relation_field_config_audit`;
- messages d’erreur sans SQL, secret, détail d’authentification ou stack trace.

## 13. RPC future

Nom recommandé pour A5.3 :

```text
public.save_relation_field_validation_draft_v0131a53
```

Signature recommandée :

```text
(
  p_table_name text,
  p_field_name text,
  p_contract_version text,
  p_validation_config jsonb
) returns jsonb
```

Séquence obligatoire :

1. obtenir `auth.uid()`;
2. exiger le rôle `Administrateur`;
3. vérifier la version et l’objet reçu;
4. vérifier table et champ non vides;
5. sélectionner `public.relation_fields` par identité logique `FOR UPDATE`;
6. refuser champ disparu ou virtuel;
7. vérifier protections et type physique/fonctionnel courant;
8. normaliser l’existant (`{}` vers objet hérité) et la proposition;
9. valider liste blanche, types, conflits, limites, `allowedValues` et messages;
10. vérifier la compatibilité contextuelle;
11. comparer les deux objets normalisés;
12. retourner `no_change` avant toute écriture si identiques et statut déjà
    `draft`, sous réserve du diagnostic de schéma;
13. sinon mettre à jour uniquement `validation_rules`,
    `configuration_status='draft'` et `updated_at`;
14. insérer l’audit commun dans la même transaction;
15. retourner la réponse structurée.

Si la configuration existante est devenue incompatible, la RPC retourne
`schema_changed`, même si la proposition est byte-à-byte identique. Une
correction administrative est nécessaire.

## 14. Contrat de réponse

Conformément à A4.2, les succès retournent `jsonb` et les erreurs sont levées
comme exceptions PostgreSQL contrôlées.

Succès avec changement :

```json
{
  "changed": true,
  "status": "draft_saved",
  "code": "saved",
  "contractName": "ValidationConfig",
  "contractVersion": "1.0.0",
  "validationConfig": {},
  "changedProperties": []
}
```

Succès sans changement :

```json
{
  "changed": false,
  "status": "no_change",
  "code": "no_change",
  "contractName": "ValidationConfig",
  "contractVersion": "1.0.0",
  "validationConfig": {}
}
```

Erreur :

- exception contrôlée, sans réponse de succès;
- SQLSTATE applicatif stable recommandé (`P0001` si aucune convention plus
  précise n’existe);
- message utilisateur système en français;
- code machine déterministe dans un détail JSON sûr;
- champ fautif facultatif;
- aucun contenu interne sensible.

Cette approche prolonge A4.2 au lieu d’introduire une seconde convention
`ok:false` incompatible.

## 16. `no_change`

Algorithme strict :

1. charger et verrouiller la ligne courante;
2. vérifier que le schéma et la protection permettent encore la configuration;
3. normaliser `{}` ou `validation_rules`;
4. normaliser la nouvelle proposition;
5. comparer les valeurs `jsonb` canoniques;
6. si identiques et `configuration_status='draft'` :
   - aucun `UPDATE`;
   - aucun audit;
   - aucun changement de `updated_at`;
   - `changed=false`;
   - `code=no_change`.

La comparaison :

- ignore l’ordre arbitraire des clés objet;
- préserve l’ordre de `allowedValues`;
- ignore l’ordre des clés de `errorMessages`;
- ne fait aucune coercition;
- ne corrige aucune valeur.

Deux listes contenant les mêmes éléments dans un ordre différent représentent
des brouillons différents.

## 17. Audit

Infrastructure réutilisée :

```text
public.relation_field_config_audit
```

Évolution additive future recommandée :

- étendre la contrainte `configuration_type` pour autoriser `validation`;
- utiliser `configuration_type='validation'`;
- `contract_name='ValidationConfig'`;
- `contract_version='1.0.0'`;
- `audit_schema_version='1.0.0'`;
- type logique d’événement `validation_draft_saved`;
- conserver `transaction_id = txid_current()::text`.

Contenu minimal :

- `relation_field_id`;
- `table_name`, `field_name`;
- `old_values` et `new_values` contenant seulement la configuration
  administrative canonique et le statut;
- `changed_properties`;
- `changed_by`/`actor_user_id`;
- rôle applicatif de l’acteur;
- `changed_at`/`occurred_at` serveur;
- `configuration_status='draft'`;
- identifiant de transaction/corrélation;
- résultat `saved`.

La table actuelle ne possède pas de colonne dédiée au rôle ni au type
d’événement détaillé. A5.3 devra décider entre une extension additive minimale
du schéma d’audit ou un emplacement versionné existant sans surcharger
`old_values/new_values`. Aucune seconde table d’audit n’est autorisée.

Aucun audit pour `no_change`. Une erreur d’insertion d’audit annule l’UPDATE.
L’audit ne contient aucune valeur métier soumise par un utilisateur.

## 18. Migration future

La future migration A5.3, non créée ici, devrait :

1. confirmer `relation_fields.validation_rules jsonb NOT NULL DEFAULT '{}'`;
2. documenter la colonne comme brouillon ValidationConfig;
3. ajouter une contrainte CHECK minimale, idéalement `NOT VALID`;
4. étendre additivement l’audit commun pour `configuration_type='validation'`;
5. ajouter les métadonnées d’audit indispensables si approuvées;
6. créer les fonctions auxiliaires immuables/stables strictement nécessaires;
7. créer la RPC versionnée;
8. fixer propriétaire, `search_path`, révocations et grant;
9. ajouter des commentaires SQL;
10. ne modifier aucune table métier ou politique RLS;
11. ne brancher aucun consommateur.

Aucun backfill destructif. `{}` reste accepté comme absence historique. Une
validation des contraintes sur les lignes existantes doit être séparée et
précédée d’un inventaire en lecture seule.

## 19. Contraintes CHECK

CHECK minimal recommandé sur `validation_rules` :

- `jsonb_typeof(validation_rules) = 'object'`;
- valeur `{}` ou objet dont les clés de haut niveau appartiennent à la liste
  autorisée;
- types manifestement invalides refusés si la condition demeure lisible et
  stable.

La CHECK ne doit pas porter :

- compatibilité avec `field_type`;
- protections physiques;
- détection complète des doublons;
- taille et points de code de chaque élément;
- règles détaillées de messages;
- audit et `no_change`.

Répartition :

| Couche | Responsabilité |
|---|---|
| CHECK JSONB | forme objet et garde structurelle minimale |
| Fonction SQL pure éventuelle | normalisation/validation JSON réutilisable et bornée |
| RPC | autorisation, ligne, protection, type, conflits, audit, no_change |
| Validateur client futur | confort UX et prévention d’appels inutiles |

La sécurité ne dépend jamais du client.

## 20. Concurrence

A4.2 utilise `SELECT ... FOR UPDATE`; A5.3 doit reprendre cette convention.

Comportement minimal :

- transaction unique implicite de la fonction;
- verrou exclusif de la ligne avant comparaison;
- second administrateur attend le premier;
- après acquisition, comparaison avec l’état réellement courant;
- aucune écriture ou audit partiel.

`relation_fields` possède `updated_at`, mais aucune révision dédiée ni jeton
attendu n’est transmis dans A4.2. Sans paramètre de concurrence supplémentaire,
le comportement est **dernier brouillon validé gagnant après verrouillage**.
Il est transactionnel mais ne détecte pas qu’un client travaillait sur un état
ancien.

Recommandation A5.3 : ajouter un paramètre facultatif
`p_expected_updated_at timestamptz` seulement après approbation. S’il diffère de
la ligne verrouillée, retourner `stale_draft` sans écriture. Ne pas créer un
système global de révisions.

## 21. Évolution du schéma

La sauvegarde refuse :

- champ ou table logique disparus;
- ligne absente du catalogue;
- `field_type` ou type physique devenu incompatible;
- champ devenu protégé, calculé, généré ou virtuel;
- limite physique devenue plus restrictive;
- propriété existante devenue incompatible;
- version de contrat inconnue.

Code privilégié : `schema_changed` lorsque la ligne existe mais que son contexte
a évolué; `field_not_found` lorsqu’elle n’existe plus.

La règle incompatible :

- reste stockée et visible en diagnostic;
- n’est ni supprimée, ni corrigée, ni migrée automatiquement;
- empêche toute nouvelle sauvegarde présentée comme valide;
- exige une correction administrative.

## 22. Séparation client/serveur

### Client futur

- normalisation présentative;
- points de code Unicode;
- erreurs immédiates;
- compatibilité indicative;
- `no_change` local pour éviter un appel;
- conservation des saisies après erreur.

### Serveur futur

- identité et existence réelles;
- session et rôle;
- protections;
- contrat et liste blanche;
- compatibilité physique/fonctionnelle;
- normalisation autoritaire;
- verrou, transaction, comparaison;
- UPDATE limité, audit et rollback.

Une validation cliente réussie ne garantit jamais la sauvegarde.

## 23. Non-consommation

Le stockage futur reste déconnecté de :

- `EditableField`;
- `universalEditorService`;
- `TerrainApp`;
- grilles et formulaires métier;
- fiches 360;
- imports et exports;
- `RelationsStudio`;
- `relationService`.

Le chargement du catalogue ne doit pas appliquer `validation_rules`. Aucun
moteur actif ne doit importer la normalisation A5. Le stockage, la sauvegarde et
une éventuelle prévisualisation administrative ne constituent pas une
activation.

## 24. Vérificateur PostgreSQL futur

Le vérificateur A5.3 devra commencer par `BEGIN READ ONLY` et terminer par
`ROLLBACK`. Il ne doit jamais appeler la RPC d’écriture.

Contrôles par métadonnées système :

- table/colonne, type `jsonb`, nullabilité et défaut;
- contrainte CHECK, état validé/non validé et définition;
- extension de la contrainte d’audit;
- signature exacte et retour `jsonb`;
- propriétaire `postgres`;
- `prosecdef=true`;
- `proconfig = ['search_path=pg_catalog']`;
- grant positif `authenticated`;
- refus `PUBLIC`, `anon` et bénéficiaires inattendus;
- propriétaires cohérents RPC/audit;
- fonctions appelées et qualification des objets;
- absence de SQL dynamique;
- cibles d’écriture limitées à deux tables;
- session et rôle Administrateur;
- version, liste blanche, protections et compatibilité;
- verrou `FOR UPDATE`;
- `no_change` avant toute écriture;
- aucun audit ni `updated_at` pour `no_change`;
- UPDATE limité aux colonnes autorisées;
- audit atomique et versionné;
- codes déterministes;
- absence de consommateur métier par preuves statiques séparées.

Les recherches textuelles de source ne sont utilisées que lorsque PostgreSQL
n’expose pas une métadonnée structurelle équivalente.

## 26. Risques

| Risque | Réduction |
|---|---|
| `validation_rules` contient un héritage historique inconnu | Inventaire préalable et acceptation temporaire de `{}` |
| `{}` confondu avec brouillon hérité | Sémantique distincte et normalisation fonctionnelle documentée |
| CHECK trop complexe | CHECK minimale, RPC autoritaire |
| Divergence Unicode | Tests points de code client/PostgreSQL |
| Limite 64 Kio calculée différemment | Mesure UTF-8 explicitement testée |
| Doublon JSON difficile à comparer | Clé type + représentation canonique |
| Messages utilisés pour masquer la sécurité | Clés fermées et messages système prioritaires |
| Perte concurrente silencieuse | `FOR UPDATE`; jeton `updated_at` recommandé |
| Règle obsolète considérée valide | `schema_changed` même sur proposition identique |
| Audit incomplet sur rôle/événement | Extension additive commune à décider |
| Accès excessif SECURITY DEFINER | search_path fermé, objets qualifiés, ACL minimales |
| Stockage pris pour activation | preuves statiques de non-consommation |

## 27. Décisions résiduelles

A5.2 résout les décisions fonctionnelles A5.1. Restent trois choix techniques
à approuver avant la rédaction SQL A5.3 :

1. **Concurrence** : autoriser ou non
   `p_expected_updated_at timestamptz`; recommandation : oui, code
   `stale_draft`.
2. **Audit du rôle et de l’événement** : autoriser l’ajout commun de colonnes
   `actor_app_role text` et `event_type text`, ou définir leur emplacement dans
   les colonnes existantes; recommandation : colonnes additives explicites.
3. **HTML dans `errorMessages`** : refus de toute chaîne contenant des balises
   ou conservation comme texte littéral non interprété; recommandation :
   refuser les balises et schémas dangereux pour rendre l’intention
   administrative non ambiguë.

Le nom final `save_relation_field_validation_draft_v0131a53` devra être confirmé
avec l’autorisation A5.3, sans autre décision d’architecture.

## 28. Recommandation pour A5.3

Après décision sur les trois points résiduels, A5.3 pourra être autorisée au
niveau du code local uniquement pour :

- une migration additive non exécutée;
- consolidation de `validation_rules`, sans nouvelle colonne concurrente;
- extension minimale de l’audit commun;
- fonction(s) pure(s) SQL strictement nécessaires;
- RPC versionnée conforme à cette spécification;
- propriétaire, search_path et privilèges minimaux;
- vérificateur `BEGIN READ ONLY`;
- tests statiques de contrat, sécurité et non-consommation;
- aucun composant, service, consommateur ou moteur d’activation.

Toute exécution PostgreSQL restera interdite sans autorisation distincte et
confirmation formelle d’une préproduction.
