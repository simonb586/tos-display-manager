# A6.1 — Contrat de brouillon PermissionConfig

**Statut : spécification additive locale**

## 1. Objet

A6.1 définit le comportement attendu du futur brouillon administratif
`PermissionConfig`. Cette sous-phase ne crée aucune permission effective et ne
branche aucun consommateur métier. Elle ne modifie ni A5, ni les rôles, ni
l’authentification, ni les politiques RLS existantes.

Le contrat `PermissionConfig` `1.0.0` déjà gelé reste la source normative :

```json
{
  "generalRule": null,
  "roleRules": null,
  "priorityStrategy": "deny-wins",
  "conservativeDeny": true
}
```

## 2. Limites de la sous-phase

A6.1 prépare uniquement la spécification du brouillon. Sont exclus :

- l’activation ou l’application des règles dans une grille, un formulaire, une
  fiche 360, Terrain, un import, un export ou une automatisation;
- toute modification de `role_ui_permissions`, de RLS ou des permissions
  serveur;
- toute déduction de droit à partir d’une configuration absente ou invalide;
- toute écriture dans une table métier;
- toute migration, connexion PostgreSQL ou exécution SQL;
- toute modification du code A5 ou conversion de ses brouillons en règles
  actives.

## 3. Règle fondamentale

`PermissionConfig` est une restriction d’interface en brouillon. Elle ne peut
jamais accorder un droit que l’authentification, le rôle applicatif, une
permission historique, une politique RLS ou le serveur refuse.

```text
droit effectif futur = droit serveur existant ET restriction UI configurée
```

Une configuration absente, inconnue, incomplète ou invalide n’élargit jamais
les droits. Tant qu’A10 n’a pas explicitement activé une version validée, le
brouillon A6 n’est consommé par aucune interface métier.

## 4. Forme d’une règle

Une règle contient exclusivement les clés booléennes tri-état suivantes :

```json
{
  "visible": null,
  "editable": null
}
```

Sémantique :

| Valeur | `visible` | `editable` |
|---|---|---|
| `false` | refus explicite d’affichage | refus explicite d’édition |
| `true` | intention d’autoriser l’affichage, sous réserve du serveur | intention d’autoriser l’édition, sous réserve du serveur |
| `null` | aucune décision A6 | aucune décision A6 |

`editable: true` ne rend jamais éditable un champ invisible, protégé,
calculé, système ou refusé par le serveur. Une clé inconnue ou une valeur d’un
autre type invalide le brouillon; elle n’est pas ignorée silencieusement.

## 5. Règle générale et règles par rôle

- `generalRule` vaut `null` ou une règle complète normalisée.
- `roleRules` vaut `null` ou un objet indexé par un identifiant de rôle connu.
- un rôle absent ne reçoit aucun droit additionnel;
- un rôle inconnu invalide la configuration pour la sauvegarde;
- le libellé affiché d’un rôle ne doit pas servir d’identifiant persistant;
- aucun rôle n’est créé, renommé ou supprimé par A6.

Le futur éditeur devra obtenir la liste des rôles depuis l’autorité applicative
existante. Il ne devra ni sonder un environnement, ni inventer une liste de
rôles à partir des données métier.

## 6. Résolution conservatrice

La stratégie est immuable : `priorityStrategy` vaut `deny-wins` et
`conservativeDeny` vaut `true`.

Pour chaque capacité (`visible`, `editable`) :

1. tout `false` explicite dans la règle générale ou la règle du rôle produit
   `false`;
2. `true` n’est retenu que si aucune source applicable ne refuse;
3. `null` reste une absence de décision et ne devient pas `true`;
4. une configuration invalide, une version inconnue ou une erreur de lecture
   produit un refus conservateur dans tout futur aperçu A6;
5. la décision serveur demeure prioritaire au moment de l’action réelle.

Exemples de projection administrative seulement :

| Général | Rôle | Projection |
|---|---|---|
| `false` | `true` | `false` |
| `true` | `false` | `false` |
| `true` | `null` | `true`, sous réserve du serveur |
| `null` | `true` | `true`, sous réserve du serveur |
| `null` | `null` | indéterminé; aucun droit accordé |

## 7. Invariants de sécurité

- `conservativeDeny` ne peut pas être désactivé.
- Une règle spécifique ne contourne jamais un refus général.
- `editable` implique une visibilité permise lors de la projection.
- Les champs d’identité, techniques, calculés ou protégés conservent leurs
  protections existantes.
- Une erreur de sauvegarde conserve le brouillon local et affiche une erreur;
  aucun fallback direct vers une table métier n’est permis.
- Aucun retry automatique d’écriture n’est permis.
- Aucun brouillon n’est activé implicitement après sauvegarde.
- Les versions et snapshots d’activation relèvent exclusivement d’A10.

## 8. Persistance future

Une sous-phase ultérieure pourra préparer une persistance additive dédiée,
versionnée et non destructive. Elle devra réutiliser l’enveloppe du catalogue
de champs, séparer le brouillon de toute configuration active et exposer une
RPC d’écriture administrative minimale.

Le SQL sera seulement préparé sous forme de fichier. Son exécution restera une
opération manuelle distincte dans SQL Editor, après autorisation explicite.

## 9. Interface future

L’éditeur A6 devra rester dans le catalogue universel et présenter :

- une règle générale visible/éditable;
- des règles par rôle connu;
- l’explication permanente « restriction UI, jamais remplacement de RLS »;
- un aperçu de résolution clairement marqué comme simulation;
- les états chargement, indisponible, lecture seule, modifié, sauvegarde et
  erreur selon les conventions A4/A5;
- aucune commande d’activation.

L’interface doit être accessible au clavier, associer chaque contrôle à son
libellé et ne pas communiquer une autorisation uniquement par la couleur.

## 10. Critères d’acceptation A6.1

A6.1 est acceptable si :

1. la portée de `PermissionConfig` est distincte d’A5 et d’A10;
2. la stratégie `deny-wins` est déterministe et documentée;
3. aucune configuration ne peut élargir une permission serveur;
4. l’absence et l’invalidité n’accordent aucun droit;
5. aucune activation, migration ou connexion externe n’est introduite;
6. les futures sous-phases peuvent implémenter séparément le modèle pur, la
   persistance SQL préparée, l’interface React et leurs tests.

## 11. Sous-phase suivante recommandée

A6.2 pourra implémenter un modèle JavaScript pur de brouillon et de projection
conservatrice, accompagné de tests unitaires exhaustifs. Elle devra rester
entièrement déconnectée des consommateurs métier et ne modifier aucun fichier
A5.
